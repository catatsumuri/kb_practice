# Score {#score}

> ScoreはSystem Oneの質問タイプであり、コンテンツを順序付けられた説明レベルに対して評価するために使用します。回答にはスコア、各レベルの確率、および確信度が含まれます。

Scoreは、ステップで説明できるスペクトラム上の位置が回答となる場合に使用します。たとえば、バグの深刻度、顧客の満足度、または候補者のPythonの経験量などです。回答が順序のない固定の選択肢の中の1つである場合は、[Choice](/primitives/choice)を使用します。はい・いいえの場合は、[Noul](/primitives/noul)を使用します。[質問タイプの選択](/primitives#choose-a-question-type)では3つすべてを比較しています。

Scoreの回答は`score`内のレベルに沿った位置であり、2つのレベルの間に落ちることもあります。モデルはまた、`probabilities`に各レベルの確率と、回答の`confidence`値を返します。

各ステップの前の数字は位置であり、[レベル](#levels)の下で説明されています。

## リクエストの構造 {#request-structure}

[TypeSafe API](/api)へのPOSTリクエストボディは、他の質問タイプと同じ3つのトップレベルフィールドを持ちます。評価するコンテンツである`state`、`model`、そして`questions`です。各Score質問には以下のフィールドがあります：

* `type`：常に`"score"`。
* `instructions`：モデルが回答する質問。評価対象となるもの。
* `criteria`：レベルの説明の順序付き配列。スケールの低い端から高い端に向かって並べます。少なくとも2つのレベルが必要で、APIは最大10個まで受け付けます。

以下は、状態がバグレポートであり、質問がバグの深刻度を問うリクエストの例です：

```json title="リクエスト" theme={null}
{
  "state": "Safariの設定ページでエクスポートボタンがクラッシュします。Chromeでは動作しますが、一部のお客様はSafariしか使用していません。",
  "questions": {
    "bug_severity": {
      "type": "score",
      "instructions": "報告された問題はどれほど深刻ですか？",
      "criteria": [
        "外観上の問題；機能への影響なし",
        "機能が壊れているか低下しているが、回避策が存在する",
        "ブロッキング問題；回避策が存在しない"
      ]
    }
  }
}
```

質問のIDはあなたが決めます。この場合は`bug_severity`です。このIDはモデルには送信されません。回答は同じIDの下に返されます。

### レベル {#levels}

`criteria`の各エントリはレベルです。考えられる回答のスペクトラム上の1点であり、言葉で説明されます。レベルの番号は`criteria`配列内の位置であり、0から始まります。したがって、上記の3つのエントリはレベル0、1、2です。配列の順序が番号付けになります。

モデルはレベルの説明のみを受け取り、各レベルは状態に対して単独で評価されます。

レスポンス内の`score`はレベルのスペクトラム上の位置です。3レベルのスケールでは0から2の範囲で、2つのレベルの間に落ちることもあります。

[クライアントSDK](/sdk)は型付き質問を提供します。Pythonでは、同じ質問は`Score`になります：

```python theme={null}
from typesafe_sdk import Score, TypeSafeClient

with TypeSafeClient() as client:
    response = client.system_one(
        state="Safariの設定ページでエクスポートボタンがクラッシュします。Chromeでは動作しますが、一部のお客様はSafariしか使用していません。",
        questions={
            "bug_severity": Score(
                instructions="報告された問題はどれほど深刻ですか？",
                criteria=[
                    "外観上の問題；機能への影響なし",
                    "機能が壊れているか低下しているが、回避策が存在する",
                    "ブロッキング問題；回避策が存在しない",
                ],
            ),
        },
    )

    print(response.answers["bug_severity"].score)
```

System Oneモデルを呼び出すには`system_one`メソッドまたは`https://api.typesafe.ai/v1/systemone`エンドポイントを使用します。`model`フィールドでリクエストを処理するモデルを選択します。[TypeSafeを使った構築方法](/concepts/how-to-build-with-system-one)では、コード内でどこから呼び出すかを説明しています。

[クライアントSDK](/sdk)を使用するか、[TypeSafe API](/api)を直接呼び出してください。コーディングエージェントが統合を記述している場合は、まず[TypeSafeエージェントスキル](/agent-skill#installation)をインストールして、リクエストとレスポンスの形式を認識させてください。

<Note>
  `instructions`と`criteria`の各レベルは、文字列、オブジェクト、または配列のいずれかにできます。まずは文字列から始めてください。レベルに説明といくつかの例示状況が必要な場合はオブジェクトを使用します。下記の[構造化レベル説明](#structured-level-descriptions)と[APIリファレンス](/api#param-instructions-2)を参照してください。
</Note>

## レスポンスの構造 {#response-structure}

レスポンスには、リクエストのIDの下に質問ごとに1つのエントリが`answers`に含まれます。以下は上記のリクエスト例へのレスポンスです：

```json theme={null}
{
  "model": "jev-1.13.0",
  "answers": {
    "bug_severity": {
      "type": "score",
      "score": 1.43,
      "confidence": 0.35,
      "legend": {
        "0": "外観上の問題；機能への影響なし",
        "1": "機能が壊れているか低下しているが、回避策が存在する",
        "2": "ブロッキング問題；回避策が存在しない"
      },
      "probabilities": {
        "0": 0.0,
        "1": 0.57,
        "2": 0.43
      }
    }
  },
  "usage": {
    "input_tokens": 332,
    "output_tokens": 18
  }
}
```

各Scoreの回答には5つの値があります：

* `type`：TypeSafeの質問タイプ。
* `probabilities`：各レベルの確率。文字列としてのレベル番号をキーとします。すべての値の合計は1です。
* `score`：レベル番号直線上の位置。0からトップレベル番号（ここでは2）まで。各レベル番号にその確率を掛けて合計した値です：0 × 0.0 + 1 × 0.57 + 2 × 0.43 = 1.43。
* `legend`：各レベル番号をその説明にマッピングしたもの。
* [`confidence`](/confidence)：`probabilities`の分布から計算された0から1の数値。1つのレベルに単一のピークがある場合は確信度が高くなります。複数のレベルに確率が分散している場合は確信度が低くなります。

スコア1.43は、モデルがレベル1とレベル2の間で分かれており、レベル1に傾いていることを意味します。これはレポートと一致します。エクスポートは壊れており、Chromeに切り替えることはほとんどの顧客にとって回避策となりますが、Safariしか使わない顧客には当てはまりません。モデルは「回避策が存在する」に0.57、「回避策が存在しない」に0.43を割り当て、分かれているため確信度は0.35です。

Python SDKを使用する場合、`ScoreAnswer`は`score`、`confidence`、`probabilities`、`legend`を型付きフィールドとして持ちます。SDKでは`probabilities`と`legend`のキーは文字列ではなく整数のレベル番号になります。

## Scoreの読み方 {#reading-a-score}

異なる入力でスコアがどのように変化するかを見てみましょう。たとえば、上記のリクエストの質問とレベルを使用します：

```
"報告された問題はどれほど深刻ですか？"
  → 0: 外観上の問題；機能への影響なし
  → 1: 機能が壊れているか低下しているが、回避策が存在する
  → 2: ブロッキング問題；回避策が存在しない
```

異なるバグレポートでスコアがどのように変化するかを確認できます：

| 状態 | `score` | `confidence` | `probabilities`：レベル0 | `probabilities`：レベル1 | `probabilities`：レベル2 |
| - | - | - | - | - | - |
| 設定ページでエクスポートボタンが数ピクセルずれています。 | 0.0 | 1.0 | 1.0 | 0.0 | 0.0 |
| PDFエクスポートボタンをクリックしても何も起きません。CSVにエクスポートして自分で変換することはできますが、非常に時間がかかります。 | 1.0 | 1.0 | 0.0 | 1.0 | 0.0 |
| PDFへのエクスポートが終わらないスピナーとともに失敗します。チームの一部はCSVエクスポートがまだ動作すると言っていますが、失敗すると言っている人もいます。 | 1.11 | 0.84 | 0.0 | 0.89 | 0.11 |
| Safariの設定ページでエクスポートボタンがクラッシュします。Chromeでは動作しますが、一部のお客様はSafariしか使用していません。 | 1.43 | 0.35 | 0.0 | 0.57 | 0.43 |
| 今朝からチームの誰もログインできません。すべての試みで500エラーが発生します。 | 2.0 | 1.0 | 0.0 | 0.0 | 1.0 |

これらの例では、確信度1.0はすべての確率が1つのレベルに集中していることを意味します。これはモデルの回答を説明するものであり、回答が正しいことを保証するものではありません。

スコアはレベル番号の確率加重平均です。3番目と4番目の例では、確率がレベル1とレベル2に分かれています。レベル2の重みが大きくなるとスコアが上がります。回避策のない顧客の割合を測定するものではありません。

異なる分布が同じスコアを生み出すことがあります。スコア1.0は、すべての確率がレベル1にある場合、またはレベル0とレベル2に半分ずつある場合を意味することがあります。これらのケースを区別するために、スコアと合わせて`probabilities`と`confidence`を読んでください。

小数のスコアは位置を表します。レポートを深刻度でランク付けするために使用したり、コードが1つの結果を必要とする場合に最も近いレベルに丸めたりすることができます。[エンティティアライメントクックブック](/cookbooks/entity_alignment)では、意思決定のために最も近いレベルに丸める例を示しています。

Scoreの確信度が低い場合、通常は3つのことのうちの1つを意味します。この状態でレベルが重複している、質問が複数のことを測定している、または状態に配置するのに十分な情報がないということです。[確信度](/confidence)のドキュメントでは、コード内での使用方法を説明しています。

## 良いレベルの書き方 {#writing-good-levels}

程度ではなく状況を説明します。「機能が壊れているか低下しているが、回避策が存在する」は、モデルが状態と照合できる何かを提供します。「適度に深刻」では意味がありません。具体的な説明はモデルがレベルを区別するのに役立ちます。既知の例に対して回答を確認してください。確信度が高いだけでは説明が優れていることを示しません。

各レベルは別々に評価されます。モデルはレベルの番号や隣接するレベルを見ないため、「前のレベルより悪い」はモデルには何も意味がなく、説明や指示の中の数字も役に立ちません。以下は、上の表のボタンのずれのレポートでレベルが数字だけの場合に起きることです：

```
instructions: "深刻度を0から2で評価してください。2が最悪です"
criteria: ["0", "1", "2"]
→ score 0.55, confidence 0.33, probabilities 0: 0.45, 1: 0.55, 2: 0.0
```

同じレポートで3つの説明的なレベルを使用するとスコアは0.0、確信度は1.0になります。数字だけでは、モデルが照合できるものがなく、確率を0と1に分散させます。

明確に説明できる限り、最大10個までのレベルを使用してください。3つでも問題ありません。明確に説明できないレベルは追加しないでください。

各Scoreの質問は1つの次元に絞ってください。説明に「時間厳守で賢くて経験豊富」と書いてある場合、その質問は3つのことを測定しており、1つが高く別のものが低い入力を配置できません。確信度が下がり、スコアの意味が薄れます。各要素に1つのScore質問に分割し、次のセクションで示すようにコードで組み合わせます。

スケールのトップに異なる対応が必要なまれな極端なケースがある場合は、それに独自のレベルを与えます。「非常に怒っている」で終わる感情スケールは「暴言や脅迫」を追加できます。そのレベルがないと、両方のメッセージがトップ近くのスコアを受け取る可能性があります。スコアだけでは区別できないかもしれません。

まったく中間がなく、回答がいくつかの離散的なカテゴリのうちの1つである場合は、代わりに[Choice](/primitives/choice)を使用するか、質問をいくつかの[Noul](/primitives/noul)の質問に分割します。自分のデータに対してレベルをテストすることが重要です。同じスケールの2つの表現がデータによって異なる動作をする可能性があります。

## 複雑な判断を複数のScore質問に分割する {#splitting-a-complex-judgment-into-several-score-questions}

複数の要素に依存する複雑な判断は、要素ごとに1つのScore質問に分割するのが最善です。その後、TypeSafeから返されたScoreをコードで組み合わせて判断を下すことができます。Score質問によって重要度が異なる場合があるため、各Score質問に相対的な重要性を表す重みを与えます。重みはあなたが決めます。組み合わせた結果がチームの判断と一致しない場合は、コードで変更して再実行します。Score質問は1つのリクエストで送信してください。並列で評価されます。質問を追加してもレスポンス時間はほとんど変わらず、少数の追加質問トークンのみコストがかかります。[複数の質問をまとめて送る](/primitives#ask-multiple-questions-together)を参照してください。

以下のリクエストは、上の表のスピナーチケットにコンテキストを追加したものです。バグの深刻度、顧客のフラストレーション、エンジニアが活用できる情報量の3つのScore質問を尋ねます。

```json title="リクエスト" theme={null}

  "state": "PDFへのエクスポートが終わらないスピナーとともに失敗します。チームの一部はCSVエクスポートがまだ動作すると言っていますが、失敗すると言っている人もいます。これで3回目の問い合わせになります。正直、もううんざりしています。手順：任意のレポートを開き、エクスポートをクリックし、PDFを選択します。macOSのChrome 128。",
  "questions": {
    "severity": {
      "type": "score",
      "instructions": "報告された問題はどれほど深刻ですか？",
      "criteria": [
        "外観上の問題；機能への影響なし",
        "機能が壊れているか低下しているが、回避策が存在する",
        "ブロッキング問題；回避策が存在しない"
      ]
    },
    "frustration": {
      "type": "score",
      "instructions": "顧客はどれほどフラストレーションを感じていますか？",
      "criteria": [
        "落ち着いて事実を述べているだけ",
        "フラストレーションを感じているが礼儀正しい",
        "非常に怒っており、強い言葉や退会の脅し"
      ]
    },
    "report_quality": {
      "type": "score",
      "instructions": "レポートはエンジニアが活用できる情報をどれほど提供していますか？",
```

各質問はチケットに対して単独で評価され、スコアが与えられます：

* `severity`は確信度0.64でスコア1.24。最初の例と同じ読み方です。エクスポートは壊れており、一部の人には回避策があります。
* `frustration`は確信度0.58でスコア1.28。言葉遣いは礼儀正しいですが、「3回目」と「うんざりしています」がスコアをトップレベルに向けて引き上げており、モデルは「フラストレーションを感じているが礼儀正しい」と「非常に怒っている」の間で0.72と0.28に分けています。このチケットではこの2つのレベルが重複しているため、確信度は中程度です。
* `report_quality`は確信度1.0でスコア3.0。手順とブラウザのバージョンが両方記載されています。

3つのスケールの長さが異なるため、組み合わせる前に各スコアを正規化します。4レベルのスケールは0から3を返し、3レベルのスケールは0から2を返すため、一方のトップスコアが他方より大きくなります。各スコアをトップレベル番号（`len(criteria) - 1`）で割ることで、すべてのスコアを0から1に揃えます。これにより重みが意味を持つようになります。severityに0.6、frustrationに0.3を設定すると、severityが2倍重要になります。

以下のTypeSafe Python SDKコードは3つの質問を送信し、各スコアを正規化して、優先度計算の例で組み合わせています：

```python theme={null}
from typesafe_sdk import Score, TypeSafeClient

TRIAGE_QUESTIONS = {
    "severity": Score(
        instructions="報告された問題はどれほど深刻ですか？",
        criteria=[
            "外観上の問題；機能への影響なし",
            "機能が壊れているか低下しているが、回避策が存在する",
            "ブロッキング問題；回避策が存在しない",
        ],
    ),
    "frustration": Score(
        instructions="顧客はどれほどフラストレーションを感じていますか？",
        criteria=[
            "落ち着いて事実を述べているだけ",
            "フラストレーションを感じているが礼儀正しい",
            "非常に怒っており、強い言葉や退会の脅し",
        ],
    ),
    "report_quality": Score(
        instructions="レポートはエンジニアが活用できる情報をどれほど提供していますか？",
        criteria=[
            "詳細なし；何かが壊れているとだけ言っている",
            "機能名は挙げているが手順や環境情報がない",
            "再現手順または環境情報はあるが、両方はない",
            "再現手順と環境情報の両方がある",
        ],
    ),
}


def normalized(answers, question_id: str) -> float:
    """トップレベル番号で割ることでスコアを0から1に揃える。"""
    top_level = len(TRIAGE_QUESTIONS[question_id].criteria) - 1
    return answers[question_id].score / top_level


def priority(ticket: str) -> float:
    with TypeSafeClient() as client:
        response = client.system_one(
            state=ticket,
            questions=TRIAGE_QUESTIONS,
        )
    answers = response.answers

    severity = normalized(answers, "severity")
    frustration = normalized(answers, "frustration")
    report_quality = normalized(answers, "report_quality")

    # 詳細なレポートはエンジニアの調査を助けるため、優先度を少し上げる。
    return 0.6 * severity + 0.3 * frustration + 0.1 * report_quality
```

上記のレスポンス例では、正規化されたスコアはseverityが0.62、frustrationが0.64、report qualityが1.0です。優先度は`0.6 × 0.62 + 0.3 × 0.64 + 0.1 × 1.0 = 0.664`であり、`0.66`に丸められます。

重みはコード内にあるため、数値がどのように作られているかを正確に確認でき、ランキングがチームの判断と一致しない場合に変更できます。後でScore質問を追加する必要がある場合は、`TRIAGE_QUESTIONS`に追加してください。リクエスト数は1のままです。この複雑な判断を個別のScoreに分解し、コードで重みを使って組み合わせる手法は[複合スコアリング](/patterns/composite-scoring)パターンと呼ばれます。
